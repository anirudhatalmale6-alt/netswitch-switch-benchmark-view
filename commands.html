The finding worth having first

MEASURED A phone that serves the pages to itself needs no certificate and loses nothing. A browser treats its own machine as trusted whatever the scheme, so plain http to localhost gets everything. The same files served from that phone to a different machine over plain http lose the storage readings.

So: run a small server on the phone, open it on the same phone, and the whole product works with no certificate to buy, expire or break.

Android is Linux, but it is not a Linux

NOT TESTED The kernel is Linux. The userland is not: Android ships a single cut-down toolbox, so many commands are missing or thinner than expected. ls, cat, ps, top and ping exist. There is no package manager, no apt, no bash by default, and no compiler.

adb shell toybox --version
adb shell toybox          # every command the phone actually has

That last line is the honest answer to "which Linux commands" — it is a different list on every handset, and the phone will print its own.

Controlling the phone from a computer

NOT TESTED This is the standard route and needs no root. Developer options on, USB debugging on, cable in.

adb devices                       # the phone should be listed
adb shell                         # a shell on the phone
adb push  site/   /sdcard/ggw/    # copy the pages onto it
adb pull  /sdcard/ggw/out.tsv .   # bring a result back
adb logcat | grep -i chromium     # watch the browser complain

Over the network instead of a cable, with the cable in once to set it up:

adb tcpip 5555
adb connect 192.168.1.50:5555     # the phone's address on the wifi

A real Linux on the phone

NOT TESTED Termux gives a proper userland on an unrooted phone — a package manager, a shell, python, a C and C++ compiler. Install it from F-Droid rather than the Play store; the Play version is abandoned and will fail on a modern handset.

pkg update && pkg upgrade
pkg install python clang git openssh termux-api
termux-setup-storage              # lets it see /sdcard

Serving the pages from the phone itself

NOT TESTED on a handset, but MEASURED as the thing that makes the readings work.

cd ~/storage/shared/ggw
python -m http.server 8080

Then open http://localhost:8080/menu.html in the phone's own browser. That is the 5 of 5 case in the table above.

To keep it alive when the screen goes off:

termux-wake-lock                  # before starting the server
termux-wake-unlock                # after

Reaching that server from somewhere else

MEASURED on the same wifi, the phone's own address works and gives the 3 of 5 case — everything except the storage figures.

ip addr show wlan0 | grep inet   # the phone's address

WILL NOT WORK from the open internet. A phone on a mobile network sits behind the operator's address translation and has no address of its own that anything outside can reach. No command fixes that; it needs a tunnel out from the phone to a machine that does have one. That is also the honest answer to whether a phone can be a public server: not by itself.

Building the C and C++ tools on the phone

NOT TESTED Termux's compiler builds the command line tools as they stand.

pkg install clang make
clang++ -O2 -o ggw_choose ggw_choose.cpp
./ggw_choose selftest

And then read the build column. The tool's own document records the same source, same machine, two compilers, moving the processor reading by 2,09 times with no hardware change. A number built by the phone's clang is not on the same axis as one built by g++ elsewhere. Tag it and never compare across tags.

Watching what the phone is doing

NOT TESTED

adb shell top -n 1                      # what is running
adb shell cat /proc/cpuinfo             # the processors
adb shell cat /proc/meminfo             # memory, in full
adb shell dumpsys battery               # charge, health, temperature
adb shell cat /sys/class/thermal/thermal_zone0/temp

Several of those are readable from a terminal and not from a browser — the battery and the temperature especially. That is the real argument for an installed app over a page: not speed, but reach.
